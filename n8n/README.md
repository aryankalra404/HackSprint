# n8n workflows

DryRun's brain, running on n8n Cloud (`https://aryankalra47.app.n8n.cloud`). The webhook shapes are defined in [../docs/CONTRACT.md](../docs/CONTRACT.md).

| Workflow | What it does |
|---|---|
| **DryRun prep** (`wf1-prep.json`) | Watches Google Calendar. For each new event, Gemini decides whether it's worth preparing for, and why. If not, the meeting is saved as `skipped` with that reason (the web app lists it with "Prepare anyway"). If so: reads your recent emails with the attendees, reads the news about the company (Google News) and its website (if there are fewer than 3 stories, it also asks Gemini to search the web, which needs billing on the Gemini key; without it the run carries on), writes the brief, seats the real external attendees as the practice panel (practice roles become one-tap suggestions with a name and face; only with no known attendee are two seated) and suggests how long to pitch (from the slot's length and the kind of meeting), saves it to the **DryRun meetings** data table and emails you. Every Gemini step (decide, research, brief) falls back to the same prompt on Groq (`openai/gpt-oss-120b`, free tier) if Gemini fails, so a quota or billing problem doesn't stop a run. It saves its progress after each stage (shown live on the web app's brief page), and if a run fails it marks the meeting failed with the reason. The web app can also add a meeting by hand: `POST /webhook/dryrun/add-meeting`. |
| **DryRun rehearsal prep** (`wf2-rehearsal-prep.json`) | `POST /webhook/dryrun/prep`, when the presenter starts a rehearsal. From the meeting's brief (in the data table), its last debrief (weak spots become objections with `source: "history"`, one more difficulty for whoever presses on them, last time's talk track per slide and the drill), the confirmed panel, the deck's slide text and the pitch length, Gemini (Groq if it fails) plans each slide (key points, target time, rescue cues), what each person will push on, who interrupts and who waits, who chairs, how many questions to ask during and after the pitch (with its reason) and where each interruption would come (`plan.interrupts`), how the chair keeps time with a pitch length (`time`; none with no limit) and short lines to voice ahead of time (the chair's time nudge and stop among them). Nothing about the meeting is fixed in code. *0.27:* for each panel member with a `twin_email`, it reads their twin from the DryRun people table: what they actually raised becomes objections (`source: "twin"`, kept only if the model names a connected fact of that twin, with its date and source) and their preferences shape their manner. It also writes a way-back-in question per slide for a presenter who freezes, and adds each person's generic lines (fillers, park, move on, hand back, the chair's "Thank you" and "Take your time", contract 0.26), which say nothing about the meeting. Each line is then voiced by Sarvam (`bulbul:v3`) in that person's voice, four at a time (a line that fails is left silent); any line the laptop already has in that voice with the same words (`cached_voices`) isn't voiced again: the generic lines after a voice's first rehearsal, and on "Run it again" every line whose words didn't change. The web app's `DRYRUN_VOICES=off` skips voicing. The webhook streams (contract 0.24): a "Report:" node after each stage sends a progress chunk, then "Send the bundle" sends the bundle. |
| **DryRun turn** (`wf3-turn.json`) | `POST /webhook/dryrun/turn`, each time the presenter has said something (the laptop forwards it from the headset with the context: the bundle, the turns so far and the open questions). Groq Whisper transcribes it (hinted with the question being answered, the company, slide titles and names), Groq decides whether anyone reacts, who, what and why, with Gemini as the fallback, then an expression node holds that to the rules (contract 0.26: every question is a thread, followed up at most once, then answered, parked or dodged and never asked again; no floor opened mid-pitch; no interruption on a title or a few words; park, move-on and hand-back use the cached generic lines), and Sarvam voices any new line (lines voiced in prep play as they are). Where no question is possible (a segment on the title slide, a few words on a slide, or nobody on the panel interrupts), "Could anyone ask?" skips the model and "Nobody reacts" answers with the transcript and a note saying why (about 0.8 s faster, fewer Groq tokens). Returns the transcript, a one-line note for the dashboard, the reactions and the threads it changed. Keeps no state. **No Code nodes on this path:** the first Code node of a run waited about 1.7 s for n8n Cloud's code runner (executions 123 and 125), so the logic runs in Set node expressions instead, which take milliseconds. |
| **DryRun meetings API** (`wf0-meetings-api.json`) | `GET /webhook/dryrun/meetings` (upcoming meetings, each with its rehearsals so far) and `GET /webhook/dryrun/meeting?id=` (one meeting with its brief, panel and rehearsals; *0.27:* each attendee's twin as counts, and the brief's "Since last time" from the twins, facts only), from the data tables. *0.27:* `GET /webhook/dryrun/twin?email=` (one twin, any of their addresses) and `GET /webhook/dryrun/twins` (everyone), from the DryRun people table. |
| **DryRun deck review** (`wf5-deck-review.json`) | `POST /webhook/dryrun/deck-review`, once per deck upload (the laptop sends it in the background after converting the slides). Reads the meeting's brief from the data table, checks the slides' claims against its research and sources, the attendees and what they care about (Gemini, Groq if it fails), and answers with 3 to 5 places the deck will get pushback: the claim, the pushback with its source, who will push and a fix. Saves it on the meeting (`deck_review`), so the next rehearsal prep presses on the same points (contract 0.26). |
| **DryRun debrief** (`wf4-debrief.json`) | `POST /webhook/dryrun/debrief`, when a rehearsal ends (the laptop sends every turn's transcript and the slide changes). A Code node counts time, words per minute and filler words per slide (the pitch only: questions asked during it are taken out of the slide's time) and pairs questions with answers; it also lists the system's own trouble for the model to discount (a transcript that looks mis-heard, the panel cutting the pitch short, turns that failed), decides whether there was enough pitch to score (45 s and 60 words), and collects the questions the presenter couldn't answer, with the meeting brief's research. The model then drafts a suggested answer with sources for each of those (contract 0.26: `owed`, leading the email); Gemini (Groq if it fails) marks the transcript with exact quotes, scores clarity, evidence, objection handling and structure with evidence, judges each person's stance, writes a talk track per slide, the drill and weak spots. It saves its progress to the **DryRun sessions** table after each step and streams it like `/prep` (the "Report: read", "Report: judged" and "Report: emailed" nodes each send a progress chunk, so the laptop no longer reads `GET /session` every few seconds), emails the report, marks the meeting `practised` and sends the whole session last. `GET /webhook/dryrun/session?session_id=` reads one session. The next `/prep` for the meeting reads its last debrief. |
| **DryRun twin** (`wf6-twin.json`) | `POST /webhook/dryrun/twin` (contract 0.27), streamed like `/prep`: builds the **twin** of one real person in the **DryRun people** table. Reads up to 20 of your emails from or to their address (and any address you linked), which are connected for sure; the real meetings they were invited to (dates for the timeline, never facts); then their full name in other people's emails, Google News and their company's own pages (home, team, about, leadership), each only a **suggestion** you confirm on the twin page. Gemini (Groq if it fails) pulls facts, each with a word-for-word quote, and up to 3 readings; the "Hold to the rules" Code node then drops any fact whose quote isn't in its source, a "promise" not from your own emails or notes, a reading without two connected facts, and a role from an unconfirmed source, and merges with what's there (no duplicates, rejected stays rejected). Each step is streamed with the sources and facts it added, and kept as the build log for Replay. Nothing from a rehearsal is read. |
| **DryRun after the meeting** (`wf8-after-meeting.json`, not exported yet) | `POST /webhook/dryrun/after-meeting` (contract 0.28), from the meeting page's "How did it go?": the presenter's voice note (cut by the laptop into pieces under 30 s) and/or typed notes. Sarvam (`saaras:v4`, Groq Whisper if any piece fails) transcribes it; Gemini (Groq if it fails) works out per attendee what they raised, what was promised and decided, each quoted; the "Hold to the rules" Code node keeps only invite attendees and quoted items and scores the hit rate against the last debriefed rehearsal's practice questions (only counts and matched real facts are kept). It updates each attendee's twin (a connected `meeting_note` source), saves `after` on the meeting (`done`) and answers the laptop; then emails the follow-up draft to the presenter (Gmail send-and-wait, up to 2 days) and sends it to the attendees only on "Send it". |
| **DryRun twin update** (`wf7-twin-update.json`) | `POST /webhook/dryrun/twin/update`: the twin page's queued changes as one batch (confirm or reject a suggestion with its facts, add a note, link another address, delete a fact, forget the person). No model call. |

## How they're built
- `build/prompts.py`: the prompts and JSON schemas. `build/build.py`: every node of every workflow (Code node JavaScript included) and the constants: `GEMINI_MODEL` (now `gemini-3-flash-preview`; free-tier limits are per model), `GROQ_MODEL`, `MIN_NEWS`, the data table id. `llm_nodes()` makes each Gemini call with its Groq fallback on the error output; Groq's JSON mode takes no schema, so the schema goes in its prompt; gpt-oss reasons before answering, so its calls ask for low reasoning effort and allow 8,192 output tokens (the default 3,072 ran out mid-answer).
- `python3 n8n/build/build.py` writes `sdk/*.ts` (`prep.ts`, `meetings-api.ts`, `rehearsal-prep.ts`, `turn.ts`, `debrief.ts`, `deck-review.ts`, `twin.ts`, `twin-update.ts`, `after-meeting.ts`), n8n Workflow SDK code. Never edit `sdk/*.ts` or the live workflow by hand: change `build.py`, rebuild, deploy.
- `wf*.json` are exports of the live workflows with credentials removed, for reading or importing elsewhere: save `get_workflow_details` to a file and run `python3 n8n/build/export.py <that file> n8n/wf3-turn.json`. For a workflow created from its SDK file and not edited in place since (the twin workflows), `export_sdk.py` takes the parameters from `sdk/*.ts` and only the positions and connections from the live copy (a small layout file), so the whole workflow doesn't have to be copied out of n8n.
- `expr_node()` in `build.py` makes a Set node whose one field is computed by JavaScript in an expression, for paths where every second shows (the live turn). Expressions accept the same JavaScript as Code nodes (checked 11 Oct: Sets, regexes, loops, spread, try/catch); `}}` in the code is written `} }`.

## Changing a workflow
The n8n MCP server is set up for this project in Claude Code (local scope, so the token isn't in the repo). With it:
1. Change `build/*.py`, run `python3 n8n/build/build.py`, and check the code with `validate_workflow`.
2. Save the live workflow (`get_workflow_details`) to a file and run `python3 n8n/build/live_ops.py n8n/sdk/prep.ts <that file>`. When the live copy is known to match the last committed build, `python3 n8n/build/sdk_ops.py <old sdk file> <new sdk file>` gives the same operations from the two builds (`git show HEAD:n8n/sdk/x.ts > old.ts`), without copying the live workflow out of n8n; it also prints `addNode` for new nodes (positions and connections by hand). It prints `update_workflow` operations for every parameter that changed, and names any new or removed nodes; add those with `addNode`, `setNodeSettings` (onError, retries) and `addConnection`.
3. Send the operations with `update_workflow`, then `publish_workflow`. Editing in place keeps the credentials attached, which the MCP server can't set up from scratch.
4. Test: add a meeting from the web app (it emails the owner) and watch the brief page, or read the run with `get_workflow_execution`.
5. Re-export `wf*.json` without credentials and commit.

## Try it
- **From the calendar:** add an event with someone outside your organisation as a guest. Within a couple of minutes it appears in the DryRun meetings table as `ready`, and you get "Your brief for … is ready". An internal event is saved as `skipped` with the reason, and shows under "Skipped by n8n" on the web app's home page. To try the skip path without the calendar, run the workflow with `test_workflow`, pinning "New calendar event" and "Worth preparing?".
- **From the web app (or curl):**
  ```bash
  curl -X POST https://aryankalra47.app.n8n.cloud/webhook/dryrun/add-meeting -H "Content-Type: application/json" \
    -d '{"title":"RouteIQ pitch","company":"Delhivery","context":"Demo for ops and finance","attendees":[{"name":"Priya Nair","email":"priya.nair@delhivery.com"}],"owner_email":"you@example.com"}'
  curl https://aryankalra47.app.n8n.cloud/webhook/dryrun/meetings
  ```
